# 架构图（arch）

> 只在 `spec.type` 为 `arch` 时读这份。其他几类看 SKILL.md 正文，不需要这份。

## 什么时候用它

讲**"系统由什么组成、分几层、谁依赖谁"**：分层架构、服务组成、部署单元。

- ✅ 接入层 / 业务层 / 数据层 这种分层图
- ✅ 一个服务由哪几个模块组成、模块之间怎么调用
- ❌ 讲调用**顺序**（先调谁后调谁）→ 用时序图
- ❌ 讲**表结构** → 用 ER 图
- ❌ 讲**业务流程** → 用流程图

## spec 格式

```json
{
  "type": "arch",
  "title": "订单服务架构",
  "layers": [
    {
      "name": "客户端",
      "modules": [{ "id": "web", "name": "Web 端" }, { "id": "app", "name": "App 端" }]
    },
    {
      "name": "接入层",
      "modules": [{ "id": "gw", "name": "API 网关", "tech": "Nginx" }]
    },
    {
      "name": "业务层",
      "modules": [
        { "id": "order", "name": "订单服务", "tech": "Spring Boot" },
        { "id": "pay", "name": "支付服务", "tech": "Go" }
      ]
    },
    {
      "name": "数据层",
      "modules": [{ "id": "mysql", "name": "MySQL", "tech": "主从" }, { "id": "redis", "name": "Redis", "tech": "缓存" }]
    }
  ],
  "links": [
    { "from": "gw", "to": "order", "label": "转发" },
    { "from": "order", "to": "mysql", "label": "读写" },
    { "from": "order", "to": "redis", "label": "缓存" }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `layers[]` | 从上到下的层，**数组顺序 = 图的上下顺序**，不要写 `y` |
| `layers[].name` | 层名，画在层的左上角 |
| `layers[].modules[]` | 这一层的模块。**每层一行**，按顺序从左到右 |
| `modules[].id` | 全图唯一，`links` 用它连 |
| `modules[].name` | 模块名（显示主体） |
| `modules[].tech` | 可选，技术栈/规格，画成下方小一号的灰字（`Spring Boot`、`主从`、`Nginx`） |
| `links[].from` / `.to` | 必须是已声明的模块 `id`；`from` 依赖/调用 `to` |
| `links[].label` | 可选，链路上写协议或动作（`HTTP`、`读写`、`MQ`） |

## 硬规则

1. **层 ≥ 1，每层至少 1 个模块**。空层没有信息。
2. **每层 ≤ 5 个模块**。超了会挤成一条线，拆图或合并成"其他"。
3. **层数 ≤ 6**。再多了读者看不完，改成两张图（部署视角 + 组件视角）。
4. **模块 id 全图唯一**，`links` 只能连已声明的模块。
5. **`links` 的箭头方向 = 依赖方向**（A → B 表示 A 调用/依赖 B）。别为了好看画双向箭头；真要双向就写两条 link。
6. **层名用"位置/职责"**（接入层、业务层、数据层），不要用产品名。
7. **同一个模块只出现一次**。为了"复用"把同一个模块画在两层里，是最常见的架构图错误——它会让"依赖关系"变得没法读。

## 不要做的事

- ❌ 画部署节点（IP、端口、容器编排）—— 这是部署图，不是本类型；真要就写进 `tech`
- ❌ 在层里画子层（三层嵌套）—— 只支持一层容器（层里放模块），嵌套会让版面失控
- ❌ 每条连接都写长句 —— `label` 是标签不是说明书，超过 6 个字就挪到正文
- ❌ 跨层连线满天飞 —— 超过 3 条跨层链路，考虑拆图

## 自检会查什么

结构：每层有模块、模块 id 唯一、连接指向已声明模块、无自连、重复连接（WARN）、连接没标签（WARN）、单层模块过多（WARN）。
几何：模块框不重叠、**每个模块必须在自己那一层里**（含 1px 容差）、连接线不穿过无关模块、线端落在框边、**连线不能穿过层名留白带**、**连线不能与模块边框重合**、标签不出画布、标签不压模块。
像素：每个模块名、技术栈字、层名都真的画上了。

## 版面约定（知道就行，不用你调）

- **层名竖排在每层左侧的留白带里**，不占模块位置，也永远不会被连线穿过（这是硬度规则，有自检兜着）。
- 同一段层间空隙里的多条线会**各自错开通道**，避免连成一条横向"搁板"。
- 绕行（上绕 / 下绕 / 侧绕）只当兜底：优先直线和 Z 型，绕行有固定代价，不会为了躲一次交叉把线甩到整层外面。
- 端口会按"另一端的位置"排序后分配，线不会一出门就互相交叉。

## 常见问题 → 怎么修

| 现象 | 修法 |
|---|---|
| 报错 `arch 需要 layers 数组` | 你写了 `nodes`，去读这份文件 |
| 报错 `第 N 条连接引用了不存在的模块` | id 拼错，或模块写在了别的层里没声明 |
| `模块必须落在所在层内` FAIL | 你手写了 `row`/`col` 之类越界字段——删掉，模块位置由层自动排 |
| `连线不能穿过层名留白带` FAIL | 说明某条跨层链路绕到了左侧——把目标模块挪到同层的另一侧，或减少跨层连接 |
| 连线穿过别的模块 | 把目标模块挪到同层的另一侧，或减少跨层连接 |
| 单层模块太多 | 合并语义相近的模块，或拆成两张图 |
